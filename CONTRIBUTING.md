# Contributing to Elastic Email projects

Thanks for taking the time to contribute! This guide applies to every repository in the [Elastic Email organization](https://github.com/ElasticEmail) that doesn't have its own `CONTRIBUTING.md`. If a repository has one, follow that instead.

## Before you start: most SDKs are generated

The official SDKs (`elasticemail-csharp`, `elasticemail-php`, `elasticemail-python` and the others) are generated by [OpenAPI Generator](https://openapi-generator.tech) from the Elastic Email REST API v4 specification.

This means:

- **Manual edits to generated files will be overwritten** by the next release.
- If an endpoint, model, parameter or description is wrong or missing, the fix belongs in the API specification. Please open an issue describing the problem. We'll fix it upstream and regenerate the SDKs.
- Pull requests are most useful for non-generated content: documentation, examples, tests, build and CI configuration, and repository tooling.

If you're not sure whether something is generated, open an issue first and ask.

## Reporting bugs

Search the repository's existing issues first. If nothing matches, open a new issue using the **Bug report** template and include:

- The package or tool version
- Your language runtime and operating system
- The API method or command you ran, with a minimal code sample
- The full error message and HTTP status code

**Never paste your API key** into an issue, log or code sample.

Questions about your Elastic Email account, sending limits, deliverability or billing aren't handled on GitHub. The preferred way to get help is the **chat widget on [elasticemail.com](https://elasticemail.com)**. See [SUPPORT.md](SUPPORT.md).

Looking for sample code? See the [Elastic Email examples repository](https://github.com/ElasticEmail/elasticemail-examples).

## Suggesting features

Open an issue using the **Feature request** template. Describe the use case first and the solution second. It helps us decide whether the change belongs in the API, an SDK, a tool or the documentation.

## Security issues

Please do **not** report security vulnerabilities in public issues. See [SECURITY.md](SECURITY.md).

## Pull requests

1. Fork the repository and create a branch from the default branch (`git checkout -b fix/short-description`).
2. Keep each change focused. One logical change per pull request.
3. Make sure the project builds and its tests pass. The repository's README explains how.
4. Update documentation if your change affects how the project is used.
5. Open a pull request against the default branch and fill in the template.

A maintainer will review your pull request and may ask for changes. When a change touches generated SDK code, we may apply it upstream instead of merging the PR directly. You'll still get credit in the release notes.

## Legacy repositories

The `ElasticEmail.WebApiClient-*` repositories contain the legacy **Web API v2** clients. They are archived and don't accept issues or pull requests. Please use the current v4 SDKs listed on the [organization profile](https://github.com/ElasticEmail).

These projects follow the [Contributor Covenant Code of Conduct](CODE_OF_CONDUCT.md). By participating, you agree to uphold it.
